# Data governance

## 1. What is sensitive here

Service requests carry three fields that identify a person:

| Field | Content | Why it exists |
|---|---|---|
| `pilgrim_ref` | Pilgrim registration reference | Links a request to the person it concerns |
| `reporter_phone` | Contact number of the reporter | Field staff call back for follow-up |
| `description` | Free text | May contain names, phone numbers, ID numbers written by staff under time pressure |

Occupancy telemetry carries none — it counts people, it does not identify them.

**All of this data is synthetic.** The governance controls are real and executed;
the personal data they protect was generated by
`src/ingestion/producers/service_request_producer.py`.

## 2. Treatment by layer

| Layer | `pilgrim_ref` / `reporter_phone` | `description` |
|---|---|---|
| **Bronze** | Stored as received | Stored as received |
| **Silver** | Replaced by `sha256(value + PII_SALT)` in `pilgrim_ref_hash` / `reporter_phone_hash`; **raw columns dropped** | Retained (not yet redacted) |
| **Gold** | Not carried | Not carried |
| **Vector store** | Never present | Redacted **before embedding** |

### Why bronze keeps the raw values

Bronze is the immutable raw record. If hashing happened at ingestion there would
be no way to correct a hashing defect, re-derive with a rotated salt, or answer a
regulator asking what was actually received. Bronze is the layer nobody queries
routinely; silver is the one everybody queries, and that is where the raw
identifiers stop.

### Why hashing rather than deletion

Hashing preserves the one analytical property that matters — you can still count
distinct reporters and notice a single person raising twenty requests — without
retaining the identifier.

### Why the hash is salted

The phone-number space is small enough to enumerate exhaustively. An unsalted
SHA-256 of `+966512345678` is reversible in seconds by hashing every candidate
number. `PII_SALT` lives in `.env`, which is gitignored, and is never committed.

Verified by [`tests/test_pii_redaction.py`](../tests/test_pii_redaction.py):
determinism under a fixed salt, divergence across salts, and non-recoverability
of the input.

## 3. Redaction before embedding — the important one

`description` is redacted **before** it is embedded, not filtered at query time.

This is the control most easily got wrong, and the reasoning is worth stating
plainly: **an embedding is derived from its source text and carries information
about it.** Once a name has been encoded into a 384-dimensional vector and
written to Qdrant, that vector retains traces of the name. Similarity search
against it can surface the containing chunk; embedding-inversion research has
repeatedly shown that meaningful fragments of source text can be recovered from
vectors alone. No query-time filter retracts any of that, because the leak is in
the stored vector, not in the retrieval logic.

Redaction therefore has to happen upstream of the encoder, or it has not happened.

Implemented in [`src/governance/pii.py`](../src/governance/pii.py):

| Pattern | Replacement |
|---|---|
| `Name: <text>` and `اسم: <text>` | `Name: [REDACTED]` |
| Phone numbers, international and local | `[REDACTED_PHONE]` |
| Digit runs of 6 or more | `[REDACTED_ID]` |

Order matters: the name marker is stripped first, because a name clause can
contain digits that the later patterns would only partially mask.

Redaction is deliberately conservative in one direction — it must not destroy
operational facts. `"station 4, level 2"` survives intact, because the SOP
retrieval depends on exactly that kind of short number. This is tested.

**Current scope:** the indexed corpus is the SOP documents, which contain no
personal data, so no redacted description has been embedded yet. The redaction
path exists and is tested ahead of the service-request descriptions being
indexed, because retrofitting it after vectors are written would require
rebuilding the collection — and would leave the old vectors in any backup.

## 4. Proof the controls ran

The silver Great Expectations suite asserts governance, not just data quality:

- `expect_column_values_to_not_be_null` on `pilgrim_ref_hash` and
  `reporter_phone_hash` — proves the hashing step executed.
- `expect_table_columns_to_match_set` with `exact_match=True` — proves the raw
  `pilgrim_ref` and `reporter_phone` columns are **absent**. GE has no
  "expect column to not exist", so pinning the exact column set is how absence is
  asserted. If either column ever reappeared, the gate fails and the pipeline
  halts.

Executed result: 11/11 expectations passing, in
[`docs/evidence/`](evidence/).

## 5. Access and retention

Personal fields in incident records are restricted and are not propagated into
analytical datasets; analytical copies carry hashed identifiers only. Retention
periods by incident severity are defined in the SOP corpus (SOP-OPS-020), and
records containing personal data are reviewed at the retention boundary so the
personal fields are removed while the operational record is kept.

## 6. Secrets

| Secret | Location | Control |
|---|---|---|
| `OPENROUTER_API_KEY` | `.env` | Gitignored; never printed; never written to evidence or cache files |
| `PII_SALT` | `.env` | Gitignored; rotating it invalidates existing hashes by design |

`scripts/verify_no_simulation.sh` checks on every run that `.env` is untracked
and that no `sk-or-v1-` key appears anywhere in git history. A key committed once
remains in history even after deletion, so the check runs before every push
rather than after.
