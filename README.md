# Hajj & Tourism Crowd Operations Data Platform

A real-time crowd operations platform for Hajj, Umrah and Saudi tourism sites. It
ingests zone occupancy telemetry and field service requests through **Kafka**,
lands them in a **Delta lakehouse** (bronze / silver / gold), enforces automated
**quality gates** that halt the pipeline on bad data, tracks **lineage** for every
stage, and serves an operations copilot that answers procedural questions grounded
in standard operating procedures with citations.

> ## ⚠️ Synthetic data disclaimer
>
> All operational data in this project is **synthetic**, generated for training
> purposes. Zone capacities, SLA targets and standard operating procedures are
> illustrative constructions and **do not represent official figures or
> procedures of any Saudi authority.** Zone and site names are real places; every
> number attached to them was generated by the producers in this repository.
> SOP numeric thresholds are informed by published public standards (Fruin
> pedestrian level-of-service bands, ISO 7243 WBGT) and are cited as such in each
> document footer — never as official policy.

## The problem it solves

Saudi crowd-management authorities operate high-density sites: the Mataf, the
Mas'a, the Jamarat bridge levels, Mina camps, Arafat and Muzdalifah, plus
year-round tourism sites at AlUla and Diriyah. Gate sensors report occupancy every
few seconds; field staff raise service requests that progress through a lifecycle
over minutes to hours.

When a zone hits 90% capacity at 2am, the duty officer needs to know the
escalation threshold, who authorises diversion, and what the medical response SLA
is — **from the actual SOP, with a citation**, not from a model's memory. That is
what this platform delivers, on top of a lakehouse that makes the occupancy
history queryable.

## Prerequisites

| Requirement | Version | Why |
|---|---|---|
| Docker | any recent | Kafka and Qdrant run as containers. Allocate **≥ 5 GB**. |
| Python | **3.11.x** | Airflow 2.10 and Great Expectations 0.18 do not run on 3.12+. |
| Git | any | — |
| RAM | 16 GB | Kafka + Qdrant (5 GB Docker) + embedding/reranker models. |
| Disk | ~10 GB | Container images, Delta tables, HuggingFace model cache (~600 MB). |

**Java is not required.** Delta is provided by `deltalake` (delta-rs, a Rust
implementation) rather than PySpark + delta-spark, so there is no JVM in the
stack.

This build was developed with `colima` as the Docker runtime (`brew install
colima docker docker-compose`, then `colima start --cpu 4 --memory 5 --disk 40
--vm-type vz`). Docker Desktop works identically.

## How to run

```bash
make up            # kafka + qdrant, wait for health, create topics
make reset         # drop delta tables, reset topic offsets and lineage stream
make produce       # 200,000 synthetic occupancy events across 7 simulated days
make ingest        # kafka -> contract validation -> bronze delta + DLQ
make gate-bronze   # Great Expectations checkpoint (exits non-zero on failure)
make silver        # bronze -> silver (dedup, reference join, utilization_pct)
make gold          # silver -> gold_zone_hourly aggregate
make test          # unit tests
make audit         # anti-substitution audit
```

Or orchestrated end to end:

```bash
make airflow       # webserver + scheduler on http://localhost:8080 (admin/admin)
```

then trigger `hajj_ops_pipeline` from the UI.

## Design decisions worth knowing

**Strict contracts.** `ConfigDict(strict=True)` on every event model. Without it
Pydantic silently coerces the JSON string `"1500"` into the integer `1500` — which
is exactly how corrupt data enters a warehouse wearing a valid disguise. Validation
runs on raw JSON **bytes** (`model_validate_json`), because Pydantic's JSON
conversion table accepts an ISO-8601 string as a `datetime` while still refusing a
quoted integer; parsing first would lose that distinction.

**Manual offset commit.** `enable.auto.commit=False`; offsets are committed only
after the batch is durably written to Delta. Auto-commit advances on poll, so a
crash between poll and write loses records silently. Committing after the write
gives at-least-once delivery — bronze can contain duplicates, which is why silver
deduplicates on `event_id` rather than trusting the stream.

**Why the quality gate fails on a 40% corruption run.** The contract keeps corrupt
records *out* of bronze, so bad values never reach Great Expectations. What GE sees
is a **volume shortfall**: the run delivers ~120k rows where ~186k were expected,
and `expect_table_row_count_to_be_between` fails. That is the Day-4 volume pillar
doing its job — catching an upstream data incident that per-row checks cannot see.

**Idempotency.** Airflow retries automatically, so a non-idempotent task
double-counts on the first retry and nobody notices until the numbers are wrong.
Silver and gold are full recomputations (overwrite); bronze ingestion is bounded
by consumer-group offsets, which do not rewind on retry.

**XCom carries only row counts and table names** — never a DataFrame. XCom values
are serialised into the Airflow metadata database.

## Configuration

| Variable | Purpose |
|---|---|
| `KAFKA_BOOTSTRAP_SERVERS` | Broker address (default `localhost:9092`) |
| `QDRANT_URL` / `QDRANT_COLLECTION` | Vector store endpoint and collection name |
| `DELTA_ROOT` | Root directory for Delta tables (default `./delta`) |
| `PII_SALT` | Salt for SHA-256 hashing of `pilgrim_ref` / `reporter_phone` in silver |
| `OPENLINEAGE_NAMESPACE` | Lineage namespace (`hajj-ops`) |
| `OPENLINEAGE_EVENTS_PATH` | Where OpenLineage JSON events are written |
| `EMBEDDING_MODEL` / `EMBEDDING_DIM` | `intfloat/multilingual-e5-small`, 384 dims |
| `RERANKER_MODEL` | Cross-encoder used for reranking |
| `OPENROUTER_API_KEY` | Generation only; retrieval is entirely local |
| `LLM_MODEL_PRIMARY` / `LLM_MODEL_FALLBACKS` | Free-model chain with fallback |
| `RRF_K` / `RETRIEVE_TOP_K` / `RERANK_TOP_K` | Retrieval tuning (60 / 50 / 5) |
